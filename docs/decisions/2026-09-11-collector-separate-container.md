# ADR: 데이터 수집기 별도 컨테이너 분리

**Status**: Accepted
**Date**: 2026-09-11
**Slice**: Cross-cutting

## Context

short-watch는 KRX, DART 등 여러 외부 소스에서 데이터를 24시간 상시 수집해야 한다. 이 수집 작업은 웹 서비스(요청-응답 라이프사이클)와 실행 패턴이 다르다 — 수집기는 스케줄에 따라 계속 돌아야 하고, 웹서비스 배포/재시작과 무관하게 유지되어야 한다.

## Options Considered

| 옵션 | Pros | Cons |
|---|---|---|
| 웹서비스 프로세스 내부에 수집 스케줄러 포함 | 배포 단순, 컨테이너 하나 | 웹서비스 재배포마다 수집 중단, 리소스 경합, 한쪽 장애가 다른 쪽으로 전파 |
| 수집기를 별도 컨테이너로 분리, 내부에서 소스별 워커 병렬 실행 | 배포/재시작 독립, 장애 격리, 웹서비스와 스케일 분리, 소스 추가 시 워커만 추가 | 컨테이너 하나 늘어남, 컨테이너 간 데이터 공유(저장소) 설계 필요 |
| 소스마다 완전히 별도 컨테이너 | 소스별 완전 독립 장애격리/스케일 | MVP 단계 소스 수(KRX, DART 등 소수)에 비해 과함, 배포/운영 복잡도 급증 |

## Decision

데이터 수집기는 웹서비스와 별도 컨테이너로 분리한다.

컨테이너 내부에서는 소스별(KRX, DART 등) 워커를 asyncio/멀티프로세스로 병렬 실행하되, 소스마다 별도 컨테이너로 쪼개지는 않는다.

동일 소스 내 연속 API 호출은 소스별로 최소 0.5~1초 간격을 강제하는 rate limiter를 둔다. 서로 다른 소스 간에는 이 제약이 적용되지 않는다(독립적으로 병렬 실행).

## Rationale

- 24시간 상시 수집과 웹서비스 요청-응답 라이프사이클이 본질적으로 다르다 — 분리해야 한쪽의 배포/장애가 다른 쪽에 영향을 주지 않는다.
- 소스마다 완전 분리 컨테이너는 현재 소스 수(KRX, DART 정도)에 비해 과한 운영 복잡도다. 워커 병렬화로 충분하다.
- 소스별 rate limit은 외부 API 차단/부하 방지를 위한 최소 안전장치다.

## Reconsider When

- 소스 수가 늘어나 하나의 소스 장애가 다른 소스 수집까지 막는 문제가 실제로 발생할 때
- 소스별 리소스 요구량 차이가 커져 개별 스케일링이 필요해질 때

이 경우 소스별 컨테이너 분리를 재검토한다.
